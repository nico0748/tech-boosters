# はじめに

2026年10月21日に、PHPの緊急のセキュリティアップデートが公開されました。
「前日に予告だけ出て、中身は翌日まで伏せられる」という、ちょっと独特な出方をしていたので、その間に何が起きていたのかを初学者向けに整理してみます。

:::note warn
この記事は、2026年10月23日時点の公開情報をもとにしています。攻撃に使える具体的な手順は書いていません。自分が管理するサーバーの確認と対策のための記事です。
:::

# そもそもPHPとは

PHPは、Webサーバーの上で動くプログラミング言語です。
ブラウザからリクエストが来ると、サーバーの上でPHPのプログラムが動いて、HTMLなどの結果を返します。WordPressもPHPで作られているので、ブログや企業サイトなど、身の回りの多くのWebサイトがPHPで動いています。

ここで大事なのは、**今回の問題は「PHPで書かれたアプリ」ではなく「PHPそのもの（言語の処理系）」にあった** という点です。
アプリ側のコードがどれだけ丁寧に書かれていても、その土台であるPHPに穴があれば影響を受けます。

# なぜ「予告だけ」して、中身を隠したのか？

ここが今回いちばん面白いところだと思います。

脆弱性の中身を修正より先に公開してしまうと、攻撃者に「ここを狙えばいい」と教えることになります。かといって、何も言わずにいきなり修正を出すと、サーバーの管理者は準備ができません。
そこで、次のような段取りが取られました。

1. **先に配る人に配る**：Linuxディストリビューションなど、PHPを多くの人に配布している事業者には、修正を先に渡して、更新パッケージを準備してもらう
2. **「いつ出すか」だけを公開する**：重大度と公開日時だけを予告して、管理者が更新の時間を空けられるようにする。中身は伏せる
3. **修正と詳細を同時に出す**：修正版が手に入るタイミングで、初めて中身を公開する

このように、見つけた人・開発者・配布する人が調整しながら、修正の準備ができてから公表するやり方を **協調された開示（Coordinated Disclosure）** と呼びます。
今回のPHPは、まさにこの流れで進んでいました。

# どんな脆弱性だったのか？

見つかったのは2件で、どちらも深刻度の指標である CVSS v4.0 で **9.2（Critical）** と評価されています。
どちらも、条件がそろうと **ログインなしで、外からサーバー上のプログラムを実行される（リモートコード実行）** おそれがあるものです。

## 前提：PHPはリクエストをどう処理しているのか

2件を理解するために、まずPHPの動き方を押さえておきます。

Webサーバーでは、PHPは「ワーカー」と呼ばれるプロセスでリクエストを処理します。
ワーカーは1回使ったら捨てるのではなく、**1つのワーカーが、何件ものリクエストを順番に処理します**。1件終わるたびに、そのリクエストで使ったメモリを片付けて（解放して）、次のリクエストに備えます。

## CVE-2026-109618：メモリが足りなくなったときの片付けの失敗

PHPには、1回のリクエストで使ってよいメモリの上限（`memory_limit`）があります。上限を超えると、PHPはその場で処理を打ち切ります。

問題は、**打ち切るタイミング** でした。
ファイルのアップロードなど、リクエストの中身を読み込んでいる途中で上限に達すると、内部のデータが「中途半端に準備された」状態のまま処理が止まります。そのあとの片付けで、正しく準備されていないメモリを解放しようとしてしまい、メモリの中身が壊れる、というものです。

## CVE-2026-109619：前のリクエストの「残りかす」を使ってしまう

こちらは、前提で書いた「1つのワーカーが順番に処理する」仕組みに関係します。

リクエストの処理中に致命的なエラーやタイムアウトが起きると、片付けが途中で止まることがあります。すると、**すでに解放したメモリを指したままの情報** がワーカーの中に残ります。
次のリクエストが同じワーカーに来たとき、その古い情報を使ってしまう。これが **use-after-free（解放後のメモリを使ってしまう）** と呼ばれる種類の不具合です。

## どの環境が影響を受けたのか

| 項目 | 内容 |
| --- | --- |
| 影響を受けるバージョン | PHP 8.5.12 / 8.4.27 / 8.3.36 / 8.2.35 より前。サポートが終わった 8.1 以前も影響を受ける |
| 影響を受ける動かし方 | Webのリクエストを処理しているもの全般（PHP-FPM、Apache の mod_php、php-cgi、FrankenPHP、LiteSpeed など） |
| 特に危険とされたもの | Apache の mod_php。アプリのコードが動く前の段階で攻撃が成立しうるとされた |
| 修正版 | 8.5.12 / 8.4.27 / 8.3.36 / 8.2.35 |
| サポート終了版 | 公式の通常の修正はなし。7.4・8.0・8.1 向けには、最低限の修正（バックポート）が公開された |

# そのとき管理者は何をしていたのか？

予告から公開までの間、サーバーを管理する側では、だいたい次のような動きがありました。

1. **自分のサーバーのPHPのバージョンを調べる**：どのサーバーで、どのバージョンが、どんな動かし方（FPM か mod_php か）で動いているかを洗い出す
2. **更新の時間を空けておく**：公開日時が予告されていたので、その時間に合わせて作業の段取りを組む
3. **公開されたらすぐ更新する**：PHP公式の修正版か、使っているLinuxディストリビューションの更新パッケージを入れる。ワーカーの再起動まで忘れずに行う
4. **すぐ更新できない場合は、一時的な緩和策を入れる**：各社の注意喚起では、次のような設定変更が挙げられていた
   - アップロードの進み具合を記録する機能（`session.upload_progress.enabled`）を切る
   - リクエストの大きさの上限（`post_max_size` など）を小さめにして、Webサーバーやプロキシの側でも制限する
   - インターネットに直接さらしているサーバーを、更新が終わるまで切り離す

ただし、一時的な緩和策はあくまで「穴を小さくする」だけで、**根本的に直すには更新するしかない** と、どの注意喚起でも強調されていました。

# 公開後の状況（2026年10月23日時点）

- 修正と同時に詳細が公開され、検証用のコード（PoC）も出回っていると報じられている
- セキュリティ企業 Rapid7 は、攻撃の試みの報告は複数あるものの、実際の攻撃で悪用されたことは確認していないとしている。また、公開されている PoC は特定のOS・バージョン・Webサーバーの組み合わせでしか動かず、どこでも通用するものではないと分析している
- 一方で、独自に再現を試みている動きがあり、より使いやすい攻撃コードが近いうちに出るおそれがあるとも指摘されている
- WordPress は、WordPress 本体の更新は不要で、PHPを更新すればよいと案内している

# この件から学べること

- **土台のソフトウェアも更新の対象**：アプリのコードだけでなく、PHPのような実行環境やOSのパッケージも、脆弱性が見つかれば更新が必要になる
- **サポートが終わったバージョンは危ない**：8.1 以前は公式の通常の修正が出ない。普段から、サポート期間内のバージョンを使っておくことが一番の対策になる
- **「どこで何が動いているか」を把握しておく**：予告が出たときにすぐ動けるかどうかは、自分のサーバーの一覧があるかどうかで決まる
- **予告が出たら準備のサイン**：中身が伏せられた予告は「準備して待っていて」という合図。公開されたらすぐ当てられるようにしておく

# まとめ

- 2026年10月21日、PHPそのものに見つかった重大な脆弱性2件（CVE-2026-109618 / CVE-2026-109619、どちらも CVSS v4.0 で 9.2）の修正版が公開された
- 公開の前日に「日時と重大度だけ」が予告され、配布する事業者には先に修正が渡されていた。修正の準備ができてから中身を公表する、協調された開示の流れだった
- 中身は「メモリが足りなくなったときの片付けの失敗」と「前のリクエストの残りかすを使ってしまう」問題で、条件がそろうとログインなしでプログラムを実行されるおそれがあった
- 根本的な対策は修正版への更新で、サポートが終わったバージョンは早めに乗り換えたい

普段なにげなく使っている土台ほど、こういうときの段取りが大事なのよ🙌

ほかにも「こういう準備をしておくといい」という知見があれば、有識者の方教えて欲しいです！
