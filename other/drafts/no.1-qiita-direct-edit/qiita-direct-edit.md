# はじめに

Qiitaの記事を、Qiita CLIとGitHub Actionsで管理しています。
`main` ブランチに記事をpushすると、Actionsが動いて自動でQiitaに投稿してくれる、よくある構成です。

便利なんですが、先日ちょっとハマりました。
記事の冒頭にロゴ画像を足してpushしただけなのに、Actionsが失敗して記事が更新されなかったんです。
原因はシンプルで、**Qiitaの画面上で記事を直接直していたこと** でした。同じ構成の人は踏みやすいと思うので、メモとして残しておきます。

# 何が起きたか

流れはこんな感じでした。

1. GitHub経由で記事を投稿した
2. 投稿したあと、気になったところをQiitaの編集画面で直接直した（タイトルと導入文の言い回し）
3. そのあと、リポジトリ側の記事に画像を1枚足してpushした
4. Actionsの投稿ジョブが失敗した

ログに出ていたのは、この1行だけでした。

```
xss-internals: 内容がQiita上の記事より古い可能性があります
```

最初は「え、今足したばかりなのに古いってどういうこと？」と思いました。

# 原因：updated_at がずれていた

Qiita CLIで管理している記事のフロントマターには、`updated_at`（最後に更新された時刻）が入っています。

```yaml
updated_at: '2026-10-19T02:38:07+09:00'
id: afb3dee0aec5805084b2
```

投稿するとき、Qiita CLIはこの `updated_at` とQiita上の記事の更新時刻を比べているようです。
Qiitaの画面で直接編集すると、Qiita上の更新時刻だけが新しくなります。リポジトリの `updated_at` は古いままです。
するとCLIから見ると「手元のファイルは、Qiita上の記事より前の版をもとにしている」ことになります。そのまま上書きすると、Qiitaで直した内容が消えてしまうので、投稿を止めてくれていたんです。

なので、このエラーは不具合ではなく安全装置でした。止めてくれて正直助かりました。

# 直し方

やることは2つです。

1. Qiita上で直した内容を、リポジトリ側の記事にも取り込む
2. フロントマターの `updated_at` を、Qiita上の記事の更新時刻に合わせる

Qiita上の今の本文と更新時刻は、公開記事ならAPIで取れます（トークンなしでも読めました）。

```sh
curl -s https://qiita.com/api/v2/items/<記事ID> | jq '{title, updated_at}'
```

本文は `.body` に入っているので、手元のファイルと見比べて差分を取り込みます。
自分の場合、差分はタイトルと導入文の数か所だけでした。それをリポジトリ側に反映し、`updated_at` を合わせてからpushすると、Actionsは無事に通ってロゴも反映されました。

ちなみに、Qiita CLIには上書きを強制するオプション（`--force`）もあります。ただ、使うとQiitaで直した内容は消えるので、取り込みを先にやるほうが安全だと思います。

# 再発防止

一番確実なのは、**記事を直すときは必ずリポジトリ側で直す** ことです。
Qiitaの画面はプレビューや誤字の確認だけに使って、本文の編集はしない。これを守れば、このエラーはまず出ないはずです。

どうしてもQiita上で直したくなったときは、直したあとに上の手順で手元へ取り込んでから、次のpushをしてください。

# おわりに

ロゴを1枚足すだけのつもりが、思わぬところで足を取られました。
でもおかげで、Qiita CLIがちゃんと「手元が古いかも」と見張ってくれていることがわかりました。
GitHubで記事を管理している人は、「Qiitaの画面では編集しない」を頭の片隅に置いておくと、地味に助かると思います。
