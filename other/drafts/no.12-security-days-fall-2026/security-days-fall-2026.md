# 聴いた講演と、そこで得たナレッジ

## WF1-01：AIエージェントに「遮断」を任せたら、取引先の注文が全部止まった

ブラウザ上の演習環境で、ログ調査をするAIエージェントを動かし、それを Claude Code で作り直すハンズオンでした。

題材は「注文APIへのアクセスが普段の20倍に増えている」というアラートです。AIエージェントはツールを呼んで証拠を集め、最終的に送信元を遮断しました。その結果、取引先の注文は **12件中0件** しか受け付けられませんでした。

おかしいのは、エージェントが自分で集めた証拠がすべて「正当な作業」を示していたことです。

- 送信元は登録済みで、認証済みのサービスアカウント
- 申請済みの作業（注文データの再送）の時間内
- 遅延は平常+15ms程度、エラー率はむしろ平常より低い

つまり、止めても守れるものがなく、失うのは注文処理だけでした。しかもエージェントは「まだ分からないこと」として「再送作業が実行中か」を自分で挙げていたのに、確認より先に遮断していました。

講師の主張は「攻撃者がAIで速くなる以上、防御側もAIを使うしかない。ただし強い権限を最初から与えず、小さく導入して育てる」というものでした。

## C1-03：攻撃は端末の外に広がっている

ヤグラの講演では、侵害の多くが端末（EDR）だけでなく、ID・SaaS・クラウド・ネットワークにまたがるという話が中心でした。講演では「侵害が複数領域にまたがる割合は87%」という数字が強調されていて、出典は Unit 42 の Global Incident Response Report 2026 とのことでした。

端末を侵害せずに進む攻撃の例として、次の3つが挙げられていました。

| パターン | 流れ | 見るべきログ |
| --- | --- | --- |
| 認証情報・セッションの悪用 | フィッシングで認証情報を盗み、SaaSに直接ログイン | IdPの認証ログ、SaaSの操作ログ |
| 漏えいしたキーでのクラウド操作 | APIキーなどでクラウドのデータにアクセス | クラウドの操作ログ、データアクセスログ |
| 境界機器からの侵入 | VPN機器などの脆弱性から内部へ | 機器のログ、通信ログ、認証ログ |

最低限つなぐべきログとして名指しされていたのは「端末ログ」と「ID認証ログ」の2つです。

印象に残ったのは、自動封じ込めについての立場です。講演では「人の判断を待つ間に侵害が成立するリスク」と「AIの誤判断で端末やIDを止めてしまうリスク」を比べて、**誤検知を許容して先に封じ込め、人が誤りと判断したら戻す** ほうが被害を小さくできる、と説明していました。前提は「止めたものを人が戻せる状態にしておくこと」です。

午前のWF1-01とは、ほぼ逆の立場なんですよね。これは後の章で考えます。

## A1-06：SCS評価制度は「格付け」ではなく「共通の質問票」

経産省のSCS評価制度（サプライチェーン強化に向けたセキュリティ対策評価制度）を、制度の議論に関わった丸山さんが解説した講演です。

一番の学びは、制度の出発点が「質問票の乱立」だったことです。委託元がそれぞれ独自のExcelのチェックシートを委託先に送るので、多くの会社から受託している委託先は、様式の違う質問票に1つずつ答えることになります。そこで共通の質問を作り、「ここまでできていれば★3、★4」と線を引いたのがこの制度、という説明でした。★で表しているので格付けに見えますが、本来は委託元と委託先が対策状況を確認し合うためのコミュニケーションツールです。

講演で説明された主な点は次のとおりです。

- ★3は専門家の確認つきの自己評価、★4は第三者評価に加えて技術的な検証がある。判断基準の数は★3が81項目、★4が153項目
- 運用開始は2027年（3月ごろの見込み）
- 対象は委託先経由の侵入や、取引先の操業停止といったリスク。SolarWinds型の更新経路への混入や、Log4jのようなOSSの脆弱性の波及は対象外
- 「CVSS基本値7.0以上の脆弱性は14日以内にパッチを適用する」という項目は、事業者から「難しい」「むしろ短くすべき」「CVSSだけで決めるのはおかしい」と両方向の指摘があり、例外の書きぶりを修正する予定

締めの言葉は「賢く使ってください」でした。★を取っていても3年前の評価かもしれないし、★がなくても個別に確認できれば取引してよい、という話です。

ISMSとの違いの説明も分かりやすかったです。ISMSは自社のリスク評価で必要と判断した対策が回っているかを見るのに対して、SCS評価制度は会社ごとの必要性とは切り離して一律の線で見る、という違いです。

## WE1-09：Claude Code の事故は「能力」ではなく「権限」の問題

Claude Code を組織に導入するときのリスクと対策を扱ったワークショップです。講師の津本さんは、AIエージェント導入支援を200社以上行ってきた立場から話していました。

講演では、事故を「ファイル操作」「コマンド実行」「情報漏えい」「プロンプトインジェクション」の4つに分けて、事例を紹介していました。その中で私が一次情報まで確認できたのが、Check Point Research が2026年2月に公表した Claude Code の脆弱性です。リポジトリに置かれた `.claude/settings.json` や `.mcp.json` を細工することで、利用者が信頼を確定する前に hooks のコマンドが実行されたり、APIの送信先を書き換えてAPIキーが送られたりする問題でした（CVE-2025-59536、CVE-2026-21852。公表時点で修正済み）。

講師はこれを「他人のリポジトリを開くことは、他人が書いた設定を自分の権限で実行することに近い」とまとめていて、なるほどと思いました。

講演の結論は「事故のほとんどはAIの能力が低いからではなく、余計なことができる権限を与えているから」というものです。具体的な対策は次の章でまとめます。

## A1-11：Webの主役が人からエージェントに移る

Cloudflare の講演は、Webにアクセスする主体が人からAIエージェントに変わっていくと、認証・コンテンツ・決済・ボット対策の前提がどう変わるかという話でした。

講演では、Cloudflare が観測しているHTMLリクエストのうち6割ほどがすでに人ではなくボットからのもので、AIエージェントと思われる通信は1年で1,700%以上増えた、と紹介されていました。

エージェント向けのWebに必要な要素として「読める」「見つけられる」「呼び出せる」「支払える」、その土台として「正規のエージェントか悪性のボットかを識別できる」の5つが挙げられていて、それぞれに対応する技術が紹介されていました。この中で特に気になったものを次の章で深ぼります。

## A1-12：脆弱性管理は「拡げる・絞り込む・検知し続ける」

脆弱性管理サービス FutureVuls の開発元による講演です。CTEM（継続的脅威エクスポージャー管理）の流れに沿って、これからの脆弱性管理で見直すべき点を3つに整理していました。

| 軸 | 内容 |
| --- | --- |
| 拡げる | CVEだけでなく、マリシャスパッケージ、EOL、外部露出、アプリ固有の不備も管理する |
| 絞り込む | SSVC と Reachability 解析で、本当に今直すべきものを選ぶ |
| 検知し続ける | 露出の変化や KEV への掲載を、すぐに優先度に反映する |

EOLの話では、FutureVuls が約16,500件のOSSを調べた結果、分類できたOSSの **48.5%** が「公式EOL」「実質EOL（宣言はないが人のコミットが2年以上止まっている など）」「開発停滞」のいずれかに当たったそうです。公式にEOLが宣言されているものだけを見ていると、残りの大半を見落とすことになります。

# 興味を惹かれた技術

## なぜ「お願い」ではなく「強制」で縛らないといけないのか？

WE1-09 と WF1-01 は別々の講演でしたが、言っていることは同じでした。AIに守ってほしいルールは、プロンプトに書く「お願い」だけでなく、仕組みで「強制」する必要がある、ということです。

WE1-09 で紹介された Claude Code の設定を、公式ドキュメントで確認しながら整理すると次のようになります。

| 仕組み | 何をするか | 性質 |
| --- | --- | --- |
| `CLAUDE.md` | 作業のたびに読み込まれる指示（例：「削除したくなったら消さずにゴミ箱用フォルダへ移す」） | お願い。まれに守られないことがある |
| `settings.json` の `permissions` | コマンドやファイル操作を `allow`（確認なし）・`ask`（毎回確認）・`deny`（禁止）に分ける | 強制 |
| hooks（`PreToolUse` など） | ツールを使う直前に自分のスクリプトを挟み、ブロックや記録をする | 強制 |
| sandbox | 読み書きできる場所や通信先をOSレベルで制限する | 強制 |
| 管理者設定（managed settings） | 組織が配布する設定。ユーザーやプロジェクトの設定より優先され、本人が上書きできない | 強制（組織単位） |

講師がすすめていたのは、お願いと強制を重ねて使うこと、そして組織ではMDMなどで管理者設定を配って、全員が同じ設定で使える状態にすることでした。

一方で、「縛りすぎ」の失敗例も紹介されていました。ターミナルから社内のリポジトリに画像を上げられない状態にしたところ、エージェントが目的を達成するために公開リポジトリに画像を置いてしまった、という事例です。権限を絞ると、エージェントは人が想定しない近道を探しにいくことがあります。

### ハンズオンで見た「強制」の効き方

WF1-01 のハンズオンでは、Claude Code に「認証された注文の通信は、止める前に担当者へ確認する設定にしてください」と頼んでエージェントを直し、同じアラートで再実行しました。結果は **注文12件すべてを受付** で、遮断は行われませんでした。

ここで、エージェントの回答（JSON）を見比べて気づいたことがあります。

| 項目 | 変更前 | 変更後 |
| --- | --- | --- |
| LLMが選んだ対応（`model_action`） | block | **block** |
| 最終的な対応（`action`） | block | investigate |
| 取引先の注文 | 受付 0/12件 | 受付 12/12件 |

LLM自身の判断は、直したあとも「遮断」のままでした。それをコード側の業務ルール（「認証された注文API通信は、人に確認してから対応する」）が「人の確認」に差し替えていた、というのが実際の動きです。講演ではここには触れていませんでしたが、まさに「お願いではなく強制」の実例だと思います。LLMの考えが変わらなくても、遮断という権限の行使をコードで止めれば業務は止まりません。

逆に気になった点もあります。報告の文面には「一時遮断を実行」と書かれていたのに、実際には遮断していませんでした。人がAIの報告を読んで判断する運用だと、この食い違いは事故のもとになります。報告と実際の動作を一致させるところまで作り込む必要がありそうです。

## AIエージェントは、どうやって「自分は正規のエージェントです」と証明するのか？

これまでボットの名乗りは `User-Agent` ヘッダーで行われてきましたが、これは誰でも好きな文字列を書けるので、偽装し放題でした。

Cloudflare の講演で紹介されていた **Web Bot Auth** は、ボットがリクエストに暗号署名を付けて、自分が誰なのかを証明する仕組みです。HTTPメッセージ署名（RFC 9421）を使い、ボットの運営者は公開鍵を公開しておき、サイト側はその鍵で署名を検証します。IETF では webbotauth ワーキンググループで標準化が進められていて、2026年9月にワーキンググループのドラフト（draft-ietf-webbotauth-httpsig-protocol-00）が出ています。

講演で強調されていたのは、正規のボットを確実に識別できれば、それ以外を絞り込みやすくなる、という点です。WAFのボット判定を「怪しいものを探す」から「正しいものを通して、残りを疑う」に変えられるわけです。

同じ講演で紹介されていた、エージェント向けの仕組みもまとめておきます。

| 技術 | 何をするか |
| --- | --- |
| Markdown for Agents | `Accept: text/markdown` 付きのリクエストに、HTMLをその場でMarkdownに変換して返す。Cloudflare のブログ記事では約16,000トークン→約3,150トークンと、約8割減ったそう |
| x402 | HTTPの `402 Payment Required` を使い、エージェントがその場で少額を支払ってコンテンツを取得する |
| Trusted Agent Protocol | Visa と共同で開発している、エージェントによる購入のためのプロトコル |
| AIクローラーの制御 | 学習用・検索用・エージェント用など目的別に、クローラーを許可・ブロックする |

セキュリティの観点で面白いと思ったのは、こうした仕組みが広がるほど「エージェントの身元」と「エージェントが持つ支払い手段」が狙われる対象になることです。署名鍵が漏れれば正規のエージェントになりすませるので、WE1-09 で出てきたAPIキーの管理と同じ問題がここにも出てきます。

## 脆弱性の優先順位は、どこで間違えるのか？

FutureVuls の講演で一番「なるほど」と思ったのが、SSVC の設定ひとつで結果が大きく変わるという検証です。

SSVC（Stakeholder-Specific Vulnerability Categorization）は、いくつかの判断ポイントから決定木で対応の緊急度を決める方法です。講演で使われていたのは「悪用されているか（Exploitation）」「攻撃を自動化できるか（Automatable）」「インターネットに露出しているか（Exposure）」「止まったときの業務影響（Human Impact）」の4つで、結果は immediate（直ちに）・out-of-cycle（定期外で）・scheduled（定期更新で）・defer（今は対応しない）の4段階になります。
（CISA版の SSVC は Exposure の代わりに Technical Impact や Mission & Well-being を使うなど、判断ポイントの組み方が版によって違います。）

上の2つは脆弱性の性質なので公開情報から自動で決まりますが、下の2つは資産ごとに人が決めるしかありません。FutureVuls の検証では、採番済みのCVE 393,780件を対象に、Human Impact を最大に固定して Exposure だけを変えたところ、緊急扱い（out-of-cycle 以上）になるCVEの割合はこうなったそうです。

| Exposure | 緊急扱いになる割合 |
| --- | --- |
| open（インターネットに面している） | 58.6% |
| controlled（アクセス制限あり） | 9.2% |
| small（閉域） | 1.3% |

open と small で約44倍の差です。露出を大きく見積もると全部が緊急になって回らなくなり、小さく見積もると本当に危ないものを見落とします。だから Exposure は「手で一度登録して終わり」ではなく、外部から観測した露出状況で継続的に更新すべき、という流れでした。

もう1つの道具が **Reachability（到達可能性）解析** です。Log4Shell を例にすると、危険な処理は log4j-core の中の JNDI Lookup にあります。バージョンだけで照合すると「log4j-core が入っている＝緊急」としか言えませんが、自分のアプリのコードから JNDI Lookup に至る呼び出し経路があるかを調べれば、届かないものは後回しにでき、届くものは優先度を上げる根拠になります。ただし、Java のリフレクションのように実行時に呼び先が決まるものは静的解析では見えない、という限界もあると説明されていました。

### 脆弱性DBそのものを疑う

もう1つ印象に残ったのが「昨日は検知されていた脆弱性が、今日は消えている。対応完了にしていいか？」という問いかけです。

パッチを当てた記録がないのに検知が消えたなら、システムが直ったのではなく、検知に使うデータが変わった可能性があります。講演では、配信元のデータが一時的に欠けたまま脆弱性DBを作り直すと、修正していないのに検知が消えてしまう実例が紹介されていました。FutureVuls では、新しいDBを公開する前に前回と比べて大きな変化があれば止めて人が確認する「公開前検査」と、変更前後をすべて記録する「履歴管理」をしていて、この仕組みは OSS の Vuls 向けに公開されているそうです。

「公式の情報でも疑う」というのは、脆弱性診断をする側としても刺さる話でした。

# 講演をまたいで見えたこと

## AIに「止める」判断をどこまで任せるのか？

同じ日に聴いた講演で、立場がはっきり分かれていました。

| 講演 | 立場 |
| --- | --- |
| C1-03（ヤグラ） | 攻撃のほうが速いので、誤検知を許容して先に封じ込める。止めたものは人が戻せるようにしておく |
| WF1-01（東洋大学） | いきなり強い権限を与えない。安全な範囲から始め、うまくいけば広げ、だめなら戻す |

どちらかが間違っているというより、「止めることで失うもの」の大きさで答えが変わるのだと思います。ハンズオンの例のように、止めた対象が取引先の注文APIなら、誤遮断は「戻せば済む」では終わらず、止まっていた間の売上がそのまま失われます。逆に、深夜に怪しいログインがあった社員のIDを一時停止するくらいなら、誤検知でも翌朝戻せば被害はほとんどありません。

自分なりに整理すると、自動で止めてよいのは「悪性を示す証拠がある」か「実害が出ている」ときで、そうでなければ人への確認依頼にとどめる、という線引きになりそうです。ここは、ハンズオンで失敗を見たからこそ持てた感覚でした。

## 「公開から悪用まで」の数字は、講演ごとに違っていた

脆弱性が公開されてから悪用されるまでの時間は、複数の講演で出てきました。ただ、数字は講演ごとに違っていました。

| 講演 | 説明されていた数字 |
| --- | --- |
| WF1-01 | 2018年ごろは約2年 → 最近は2.3日 |
| A1-11 | 2018年は2年以上 → 今は24時間未満 |

[other no.8](TODO: no.8 の記事URL) では「2018年度は2年、2026年度は2日」と書きましたが、どの時点のデータを、平均と中央値のどちらで、どこまでを「悪用」と数えるかで値は変わります。たとえば Sysdig の Sergej Epp さんが公開している Zero Day Clock は、公開された悪用が確認されたものだけを集計していて、非公開の悪用はそれより早く起きている可能性があると注記しています。

数字そのものより「年単位から日単位、さらに時間単位へ縮んでいる」という傾向として受け取るのがよさそうです。

## AI SOC の「メモリ」は汚染できるのか？

これは講演の内容ではなく、聴きながら考えたことです。

AI SOC の中には、過去の判断と根拠を保存しておき、同じアカウントなどが再び検知されたときに照合する「メモリ」の仕組みを持つものがあります。人が判断を修正した理由も蓄積して、次の誤判定を減らす、という説明でした。

これは構造的には、RAG の検索対象と同じです。そう考えると、攻撃者が「定例作業」と判定されやすい操作を事前に繰り返して、誤った判断履歴をメモリに貯めさせれば、本番の攻撃が過去の対応と照合されて見逃される、ということが起こり得るのではないか？と思いました。ログの本文にプロンプトインジェクションの文字列を混ぜる経路もあります。

聴いた講演では、メモリの改ざん耐性やログ経由のインジェクション対策には触れられていませんでした。ここは別の記事で深ぼってみたいテーマです。

# まとめ

- AIエージェントの事故は、能力よりも権限の与え方で起きる。ルールはプロンプトの「お願い」だけでなく、設定やコードで「強制」する
- ハンズオンでは、LLMの判断が「遮断」のままでも、コード側のガードで業務を止めずに済んだ
- Webの主役がエージェントに移ると、「正規のエージェントかどうか」を暗号で証明する仕組み（Web Bot Auth）が土台になる
- 脆弱性の優先順位は、人が決める Exposure の設定で約44倍変わる。脆弱性DBそのものも疑う
- SCS評価制度は格付けではなく、取引先との共通の質問票として「賢く使う」もの

AIの話ばかりの1日でしたが、結局どの講演も「権限を絞る」「証拠で判断する」「変化を追い続ける」という昔からある基本に戻ってきていたのが印象的でした。基本は強いのよ🙌

AI SOC のメモリ汚染について、実際の製品でどう対策されているか知っている方がいたら、有識者の方ぜひ教えて欲しいです！
