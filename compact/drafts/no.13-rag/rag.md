# はじめに

社内ドキュメントに答えるチャットボットの話でよく出てくる RAG を、仕組みと気をつけどころに絞ってまとめておきます。

# ひとことで言うと

**RAG（Retrieval-Augmented Generation、検索拡張生成）は、質問に関係する文書を検索して、その内容をプロンプトに入れてから LLM に答えさせる方法**です。
LLM が学習していない情報（社内資料、最新の情報）にも答えられるようになります。

# 仕組み

## 準備（インデックスを作る）

1. 文書を、数百文字くらいのかたまり（チャンク）に分ける
2. 各チャンクを埋め込みモデルでベクトルにする
3. ベクトルとチャンクを、ベクトルデータベースに入れておく

## 質問が来たとき

1. 質問もベクトルにする
2. ベクトルデータベースから、似ているチャンクを上位 k 件取り出す（Retrieval）
3. 取り出したチャンクを、質問と一緒にプロンプトに入れる（Augmented）
4. LLM が、そのチャンクをもとに答えを作る（Generation）

# ファインチューニングとの違い

| | RAG | ファインチューニング |
|---|---|---|
| 知識を足す方法 | 検索して、プロンプトに入れる | モデルの重みを追加で学習する |
| 情報の更新 | 文書を入れ替えるだけ | 学習し直す |
| 根拠の提示 | 取り出した文書を示せる | 示しにくい |
| 向いているもの | 事実や文書の内容に答える | 口調・形式・特定のタスクのやり方を覚えさせる |

# 精度を上げる工夫

- **ハイブリッド検索**：ベクトル検索と、キーワード検索（BM25 など）を組み合わせる
- **リランキング**：取り出した候補を、別のモデルで並べ直してから使う
- **チャンクの切り方**：見出しや段落の区切りに合わせる、前後を少し重ねる

# セキュリティで気をつけること

- **間接プロンプトインジェクション**：検索された文書に「この指示に従え」と書かれていると、LLM がそれに従ってしまうことがある
- **アクセス制御**：ユーザーが本来見られない文書が検索結果に出てこないよう、検索の段階で権限を絞る
- **データの汚染**：検索対象の文書を書き換えられると、間違った答えを返すようになる

RAG を使っても、ハルシネーション（もっともらしい間違い）は減らせるだけで、なくなるわけではありません。

# まとめ

RAG は「調べてから答える」を LLM にやらせる仕組みで、検索の質と、検索される文書の安全性がそのまま答えの質になるのよ。
もっと良い対策があれば、有識者の方教えて欲しいです！
